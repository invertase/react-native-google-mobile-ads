Interstitials are full-screen ads that cover the interface of an app until closed by the user. These types of ads are
programmatically loaded and then shown at a suitable point during your application flow (e.g. after a level on a gaming
app has been completed, or game over). The ads can be preloaded in the background to ensure they're ready to go when needed.

To create a new interstitial, call the `createForAdRequest` method from the `InterstitialAd` class. The first argument
of the method is the "Ad Unit ID". For testing, we can use a Test ID, however for production the ID from the
Google AdMob dashboard under "Ad units" should be used:

```js
import { InterstitialAd, TestIds } from 'react-native-google-mobile-ads';

const adUnitId = __DEV__ ? TestIds.INTERSTITIAL : 'ca-app-pub-xxxxxxxxxxxxx/yyyyyyyyyyyyyy';

const interstitial = InterstitialAd.createForAdRequest(adUnitId, {
  keywords: ['fashion', 'clothing'],
});
```

The second argument is additional optional request options object to be sent whilst loading an advert, such as keywords, location, and content URLs.
Setting additional request options helps AdMob choose better tailored ads from the network.
View the [`RequestOptions`](https://github.com/invertase/react-native-google-mobile-ads/blob/main/packages/core/src/types/RequestOptions.ts) source code to see the full range of options available.

### Content URL targeting (brand safety)

When an ad sits next to web-like content (for example an article in a feed), you can pass the page URL and nearby URLs so Google can apply a more appropriate content rating.

- `contentUrl`: the URL of the content currently being displayed (max 512 characters, HTTP or HTTPS).
- `neighboringContentUrls`: up to 4 nearby content URLs (each max 512 characters, HTTP or HTTPS).

These options apply to any ad loaded with `RequestOptions` (`createForAdRequest`, banner `requestOptions`, [hooks](/ad-formats/hooks), [native ads](/ad-formats/native)).

```js
import { InterstitialAd, TestIds } from 'react-native-google-mobile-ads';

const interstitial = InterstitialAd.createForAdRequest(TestIds.INTERSTITIAL, {
  contentUrl: 'https://www.example.com/article-a',
  neighboringContentUrls: [
    'https://www.example.com/article-b',
    'https://www.example.com/article-c',
  ],
});
```

See Google's [brand safety targeting](https://developers.google.com/ad-manager/mobile-ads-sdk/android/targeting#content_url) docs for platform details.

The call to `createForAdRequest` returns an instance of the [`InterstitialAd`](https://github.com/invertase/react-native-google-mobile-ads/blob/main/packages/core/src/ads/InterstitialAd.ts) class,
which provides a number of utilities for loading and displaying interstitials.

To listen to events, such as when the advert from the network has loaded or when an error occurs, we can subscribe via the
`addAdEventListener` method:

```jsx
import React, { useEffect, useState } from 'react';
import { Button, Platform, StatusBar } from 'react-native';
import { InterstitialAd, AdEventType, TestIds } from 'react-native-google-mobile-ads';

const adUnitId = __DEV__ ? TestIds.INTERSTITIAL : 'ca-app-pub-xxxxxxxxxxxxx/yyyyyyyyyyyyyy';

const interstitial = InterstitialAd.createForAdRequest(adUnitId, {
  keywords: ['fashion', 'clothing'],
});

function App() {
  const [loaded, setLoaded] = useState(false);

  useEffect(() => {
    const unsubscribeLoaded = interstitial.addAdEventListener(AdEventType.LOADED, () => {
      setLoaded(true);
    });

    const unsubscribeOpened = interstitial.addAdEventListener(AdEventType.OPENED, () => {
      if (Platform.OS === 'ios') {
        // Prevent the close button from being unreachable by hiding the status bar on iOS
        StatusBar.setHidden(true);
      }
    });

    const unsubscribeClosed = interstitial.addAdEventListener(AdEventType.CLOSED, () => {
      setLoaded(false);
      if (Platform.OS === 'ios') {
        StatusBar.setHidden(false);
      }
      // Preload the next ad on the same instance.
      interstitial.load();
    });
    const unsubscribePaid = interstitial.addAdEventListener(AdEventType.PAID, event => {
      console.log('Interstitial revenue', event.value, event.currency);
    });

    // Start loading the interstitial straight away
    interstitial.load();

    // Unsubscribe from events on unmount
    return () => {
      unsubscribeLoaded();
      unsubscribeOpened();
      unsubscribeClosed();
      unsubscribePaid();
    };
  }, []);

  // No advert ready to show yet
  if (!loaded) {
    return null;
  }

  return (
    <Button
      title="Show Interstitial"
      onPress={() => {
        // Not loaded, already showing, or a platform decline reject; a destroyed ad throws.
        interstitial.show().catch(console.warn);
      }}
    />
  );
}
```

The code above subscribes to the interstitial events (via `addAdEventListener()`) and immediately starts to load a new advert from
the network (via `load()`). Once an advert is available, local state is set, re-rendering the component showing a `Button`.
When pressed, the `show` method on the interstitial instance is called and the advert is shown over-the-top of your
application.

You can subscribe to other various events with `addAdEventListener` listener such as if the user clicks the advert,
or closes the advert and returns back to your app.
To see the full list of available events, view the [`AdEventType`](https://github.com/invertase/react-native-google-mobile-ads/blob/main/packages/core/src/AdEventType.ts) source code.

The sample reuses the same `InterstitialAd` instance: after `CLOSED`, it calls `load()` again so the next
advert is ready for the next transition.
Forward `AdEventType.PAID` payloads to your
[revenue telemetry](/revenue-telemetry-and-auction-diagnostics) pipeline.

## Caveats / limitations

### Android: host UI flicker after fullscreen dismiss

After a normal close of an interstitial, app open, rewarded, or rewarded interstitial ad on Android, some apps see the
host screen briefly **push and return** (a one-frame layout jump / flicker). iOS is often unaffected because fullscreen
ads present from a view controller, not a separate activity with its own window and system UI policy.

On Android, Google Mobile Ads shows those creatives in Google's own `AdActivity` (classic:
`com.google.android.gms.ads.AdActivity` with `@android:style/Theme.Translucent`; Next-Gen:
`com.google.android.libraries.ads.mobile.sdk.common.AdActivity` with `@style/Theme.GoogleMobileAds`). When that activity
finishes, your `MainActivity` resumes. System bars, immersive mode, window insets, soft-input mode, and activity
transitions can all change in that resume transition. React Native layout (Safe Area, `react-native-screens`, keyboard
controllers, navigation stacks) then recalculates — which can look like a push/back flicker even though no navigation
`push` / `pop` ran.

This package's Android show path only:

- calls the SDK `show(activity, …)` APIs,
- optionally forwards `show({ immersiveModeEnabled })` to `setImmersiveMode(boolean)` (Android system UI immersive
  mode on the ad window — **not** a host-window or React Navigation API),

then emits `AdEventType.CLOSED` from `onAdDismissedFullScreenContent`. It does **not** set `MainActivity` window
flags, `windowSoftInputMode`, override activity transitions, or drive React Navigation / `react-native-screens`.

This is a **different** class from [fullscreen ads closing after Home → resume](#android-fullscreen-ads-closing-after-home--resume)
(`singleTask` clearing `AdActivity`). Here the ad closed intentionally; the host UI is what jumps.

Ways to investigate or mitigate in **your** app (not in this library):

1. Re-test with `immersiveModeEnabled` omitted or `false`. Leaving immersive mode when `AdActivity` finishes is a
   common source of system bar / inset restore animation on the resumed activity.
2. Check `MainActivity` `android:windowSoftInputMode` (templates often use `adjustResize`). A focus or inset change on
   resume can resize the React root once; try `adjustPan` or `adjustNothing` if that matches your keyboard behavior.
3. Prefer current Google Mobile Ads / Play services builds and compare against a minimal native AdMob sample (no React
   Navigation). Tip pins: `packages/core/package.json` `sdkVersions`. Classic creative chrome still ships via the
   remote GMS ads module.
4. If the jump tracks Safe Area or navigation chrome, audit app-side listeners on `AdEventType.CLOSED` /
   `AppState` that remount screens, toggle status-bar style, or call navigation `reset` / `navigate` — those are app
   code, not this package.
5. Activity enter/exit animations and translucent `AdActivity` themes are owned by the SDK / your app theme. Do **not**
   expect this React Native package to zero Google's transitions or pad host insets after dismiss.

If a pure Google Mobile Ads sample still flickers on the same device / OS, escalate to Google with Mobile Ads SDK logs.
This package cannot keep host layout stable across Google's `AdActivity` finish.

On Android 15+ (`targetSdk` 35+), if interstitial content draws under the system navigation bar, see
[Android: interstitial content under the system navigation bar (API 35+)](#android-interstitial-content-under-the-system-navigation-bar-api-35).

### Android: interstitial content under the system navigation bar (API 35+)

On Android 15+ (`targetSdk` 35+), the platform can enforce edge-to-edge drawing on activities. Google Mobile Ads presents
fullscreen creatives (interstitial, rewarded, rewarded interstitial, app open) in Google's own `AdActivity`, not in a
view owned by this package:

- Classic SDK: `com.google.android.gms.ads.AdActivity` with `@android:style/Theme.Translucent`
- Next-Gen SDK: `com.google.android.libraries.ads.mobile.sdk.common.AdActivity` with `@style/Theme.GoogleMobileAds`
  (transparent status and navigation bar colors)

This package calls `show()` and forwards Google's fullscreen callbacks. It does **not** apply `WindowInsets`, host the
creative layout, or replace Google's activity theme. If interstitial (or other fullscreen) content draws under the
system navigation bar on API 35+, that layout is controlled by the Google Mobile Ads SDK / GMS module for `AdActivity`.

Ways to mitigate this in **your** app (not in this library):

- Prefer a current Google Mobile Ads SDK build and re-test after SDK / Google Play services updates. This package's tip
  pins live in `packages/core/package.json` `sdkVersions`; they do **not** freeze classic fullscreen creative layout —
  classic UI is delivered by the remote GMS ads module, not a fixed in-app layout in the client AAR.
- Temporary app-side opt-out: define a custom theme that **parents** the SDK theme your backend already uses
  (`@android:style/Theme.Translucent` for classic, `@style/Theme.GoogleMobileAds` for Next-Gen) and **only adds**
  `android:windowOptOutEdgeToEdgeEnforcement=true` (API 35+ only; typically under `res/values-v35/`). Do **not** replace
  those parents with an opt-out-only theme — that can break translucent / transparent-bar behavior on `AdActivity`.
  Then merge-override Google's `AdActivity` in **your** `AndroidManifest.xml` with the matching `android:name`,
  `tools:replace="android:theme"`, and `xmlns:tools` on the manifest root. Opt-out is a platform migration escape
  hatch — validate immersive / video creatives and plan to remove it when the SDK no longer needs it.
- Do **not** expect this React Native package to pad Google's `AdActivity` content; there is no public bridge API for
  that window.

Minimal classic example (Next-Gen: parent `@style/Theme.GoogleMobileAds` and
`com.google.android.libraries.ads.mobile.sdk.common.AdActivity`):

```xml
<!-- res/values-v35/styles.xml -->
<style name="Theme.AdActivity.OptOutEdgeToEdge" parent="@android:style/Theme.Translucent">
  <item name="android:windowOptOutEdgeToEdgeEnforcement">true</item>
</style>
```

```xml
<!-- AndroidManifest.xml -->
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
  xmlns:tools="http://schemas.android.com/tools">
  <application>
    <activity
      android:name="com.google.android.gms.ads.AdActivity"
      android:theme="@style/Theme.AdActivity.OptOutEdgeToEdge"
      tools:replace="android:theme" />
  </application>
</manifest>
```

- On Android, if an app open ad closes when returning from the background via the launcher icon, see
  [Android: fullscreen ads closing after Home → resume](#android-fullscreen-ads-closing-after-home--resume).
### Android: fullscreen ads closing after Home → resume

On Android, Google Mobile Ads presents interstitial, app open, rewarded, and rewarded interstitial creatives in a separate
`AdActivity`. This package only emits `AdEventType.CLOSED` when that activity reports dismissal
(`onAdDismissedFullScreenContent`). Other helpers may listen to React Native `AppState` (for example `useForeground` /
`AdPoolProvider`), but they do **not** destroy a showing fullscreen ad or emit `CLOSED` from `AppState` alone.

If a fullscreen ad disappears when the user presses Home and then returns via the **launcher icon**, check your app
`AndroidManifest.xml` `MainActivity` `android:launchMode`. React Native and Expo templates commonly set
`android:launchMode="singleTask"`. With that mode, bringing `MainActivity` to the front can clear activities above it in
the same task — including Google's `AdActivity` — which dismisses the creative and fires `CLOSED` (including before any
delayed close button appears).

Ways to mitigate this in **your** app (not in this library):

- Prefer `android:launchMode="singleTop"` on `MainActivity` when it is compatible with your deep-link and cold-start
  behavior (Flutter AdMob samples commonly use `singleTop`).
- After Expo prebuild, edit the generated `android/app/src/main/AndroidManifest.xml`, or apply the same change with a
  small config plugin, then re-verify launcher resume and any auth / deep-link flows that originally needed `singleTask`.
- Confirm the dismiss is not your own JS calling `destroy()` / reloading on `AppState` `'active'`.

This package cannot keep Google's `AdActivity` alive across an app-manifest task clear. Changing `launchMode` has
side effects beyond ads — validate carefully before shipping.
